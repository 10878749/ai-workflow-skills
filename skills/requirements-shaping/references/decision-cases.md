# 判断示例

以下是概括案例，不是当前项目事实。

| 情形 | 决策要点 |
|---|---|
| 行业服务平台被做成各类论坛列表 | 重新明确服务、需求、企业展示、云工具和交流的职责；按使用路径决定独立页面 |
| 用户要“拿给别人看懂”的 Demo | 把产品定位、模块关系和展示路径作为本阶段成功条件；真实功能与模拟内容明确区分 |
| 用户说“现有排版不动，只换底图” | 将版式列为保留行为，检查替换是否影响可读性和输出；不顺便改版 |
| 用户要求多个端都要有，但先快速试用 | 根据首个使用场景选择当前可验证载体，记录其他端的依赖；不把一次 H5 编译扩称全端可用 |
| 用户已说按方案实施 | 简短核实变化后直接做，重要范围变化再处理，不重复等同一批准 |
| 用户说“保证可扩展” | 指出已知的后续变化和最小接口／结构预留，用一个变化示例验证；不预建所有未来模块 |
| 早期规格和用户最新纠正冲突 | 更新同一权威入口和受影响阶段，注明取代关系；旧文档不继续作为当前约定 |

把“用户想看懂”“用户想试用”“用户想正式交付”混成一个目标，会让阶段范围失真。用当前任务目的决定本轮需要多深的实现与证据。
