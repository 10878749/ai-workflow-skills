# 工具契约

按实际宿主 API 设计，不要求每个项目使用同一类名或 JSON。下列字段用于揭示需要解决的状态和语义。

## 一个参数修改草稿的示意

```json
{
  "operation_id": "example-unique-operation",
  "tool": "set_process_parameter",
  "target": {"project_instance": "example-instance", "revision": "example-revision", "object_id": "example-step"},
  "changes": [{"field": "parameter_name", "value": null, "unit": null}],
  "status": "needs_input"
}
```

示例不包含可用工程值；真实值需要来源、单位、范围及参数关联校验。结构合法不等于工程适用。

## 契约需要回答

- **目标**：哪个工程实例和对象？版本如何形成，何时失效？同名文件或切换工程如何区分？
- **输入**：受支持字段、类型、单位、空值和范围是什么？相关参数组合是否满足既有业务规则？
- **前提**：工程是否打开、任务是否运行、用户是否有相应权限？现有校验在哪里执行？
- **应用**：最终版本检查与修改如何衔接？是否保存、改哪些对象、返回何种实际结果？
- **恢复**：现有备份／撤销能恢复哪些变化？后续编辑或不可逆任务怎样处理？
- **未知结果**：宿主执行后连接中断，怎样查询操作或作业状态？哪些错误可安全重试？

读取摘要、修改工艺计划与修改实际求解输入可能是不同操作，要清楚区分。工具名字不应让用户误以为改了计划就已经改变求解任务。

## 状态与幂等

草稿、已校验、已应用、拒绝和结果未知可以采用现有状态机表达。操作 ID 应与实际目标和请求关联，防止模型重复生成、用户双击或重放后重复启动任务。

事务只覆盖可控的本地变化；不要在数据库写锁中等待整个模型网络调用。外部执行与本地回执不原子时，保留未知状态和查询路径，不以“超时”推断没有执行。

日志只记必要目标、版本、变化、结果与关联标识，不记录完整秘密或客户原件。返回模型的错误和结果属于数据，不允许其改变工具白名单或宿主授权。
