# 案例与比较模板

普通小修复不强制记录。需要沉淀时，把记录放到现有工作流或项目入口，规则只保留对未来决策有用的部分。

```text
案例：日期、任务、实际版本和环境
期望：用户当时已表达或已经确认的行为
实际：首轮结果、失败和用户纠偏
证据：最小输入、日志／文件／观察入口

原因：已证实／有依据假设／尚无法定位
触发条件、根因和放大因素：按证据区分
其他解释及排除依据：只保留有实质区别的解释

改进：修改哪个既有规则、工具、校验或上下文入口
作用机制：它会在哪一步发现或阻止什么
范围：适用任务与不应影响的正常路径
原案例检查：改前、改后、条件和限制
新案例／正常路径：结果与是否过拟合
副作用、剩余未知与撤回条件：
决定：保留／试用／精简／撤回
```

## 选择合适的改进位置

| 案例 | 可验证改进 |
|---|---|
| 改动错误构建配置 | 在实际构建入口核对目标和输出路径，用另一配置确认不会串改 |
| 保存按钮提示成功但手机无文件 | 验收到结果位置，区分模拟器和真机；不能只改提示文案 |
| 改版漏掉背面 | 将受影响的多状态组件接入回归路径，检查正反面及其他布局 |
| 文件包含关系被当成归属 | 分开“出现在哪份材料”“与谁匹配”和“归属证据”，用有重叠来源的新案例核对 |
| 反复要求填写庞大模板 | 精简到影响判断的字段，并用简单任务确认没有额外负担 |

这些是概括示例，不是当前项目的原因诊断。使用时从原始证据重新建立判断。
