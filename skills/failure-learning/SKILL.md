# 失败复盘与流程改进

把已有工作循环的外层复盘提炼成专项方法：真实案例 → 可核对原因 → 最近的一层改进 → 旧新案例检查 → 保留、精简或撤回。

## 先恢复事实

读取本次目标、实际对象和版本、原始输入、用户反馈、首次失败与后续记录。区分当时已有约定、后来改变的需求、执行者的推断和工具限制；不要把所有纠偏归为用户提示词不够好。

记录期望与实际行为，以及用户为了发现、解释或修复问题做了什么。使用最小必要证据，不复制完整私有聊天、原件或秘密配置。旧案例可以支持假设，但不能冒充当前复现。

用户只要求复盘时给出事实、原因置信度和具体改进建议；已授权修复或改进时完成相应工作与验证，不重复等确认。需要先恢复当前任务时，优先完成已授权恢复，不让复盘替代实际交付。

## 解释为什么会发生

沿目标、上下文、对象识别、工具执行、状态、检查和交付链寻找最先发生的偏差。列出少量有区别的原因及可验证信号，区分触发条件、根因和放大因素。

“没注意”“加强测试”“下次更谨慎”没有解释具体漏检位置。把它转换为可观察机制，例如改动了另一构建配置、检查的是预览而非相册、卡片背面未进入回归路径，或统计时把文件包含关系误当归属。

权限拒绝、环境错误与产品缺陷分别处理。偶发失败需要有界对照，复跑成功本身不能证明原失败无风险；无法唯一定位时保持假设，不编造确定根因。

## 改最近的一层

选择与证据相符、能减少同类失败的最小改进：

- 当前对象或稳定事实不清：更新已有交接、版本入口或上下文选择。
- 可机械判断的行为漏检：补到实际执行的测试、校验或交付检查中。
- 工具语义或运行机制有缺口：修工具边界、状态、错误或恢复路径。
- 项目长期约定缺失：更新适用的 `AGENTS.md` 或已有规则入口。
- 跨任务反复出现的判断缺失：更新相关 skill；单次细节不扩成全局长指令。

保留用户意图、既有授权和正常工作方式。不要为避免一种失败给所有小任务加审计、审批、长记录或全量测试。不要为了通过而放宽要求或删除反例。已有工作循环继续负责总体执行，本技能只维护复盘案例与对应改进。

## 验证改进是否有用

使用原失败案例及至少一个相关的新变化或正常路径。尽量保持输入、环境与验收可比；有基线时核对改进前是否暴露问题、改进后是否解决。基线不可运行时明确限制，不把事后描述当实验。

检查是否只记住原句、路径或示例，是否误伤其他项目／任务，是否把错误转移到另一层。一次改变少量因素；缺乏稳定证据时，把改进作为试用规则并给出撤回条件。

可以观察重复纠偏、必要人工介入、返工、耗时和已知成本，但不为没有记录的量填数，也不凭一次成功宣称总体效率提升。模型、环境或需求变化会限制比较。

## 留下可维护的经验

复用已有案例和验证入口，按 [案例与比较模板](references/case-and-comparison.md) 裁剪。记录证据、原因置信度、实际改动、原新案例结果、副作用和保留／撤回判断。

最终说明当前问题是否解决、哪一层改进了、凭什么认为有效、仍有哪些未知，以及下一次怎样发现同类失败。避免把“写了一条规则”或“结构检查通过”当成执行行为已经改善。
