# 项目接手与续接

让下一位执行者找准对象、恢复必要环境，并沿用真实进展继续工作。适用于本地、云端、桌面软件、Web 项目和多仓库组合；不依赖特定操作系统或连接器。

## 先确定本轮要交付什么

从用户目标和已有授权选择处理方式，不反复要求确认：

- **只读接手／找版本／先给方案**：核实并解释现状，给出可执行步骤。交接草案先在聊天呈现；未经请求不修改项目记录、分支、源码或运行环境。
- **接手后继续开发／修复／恢复运行**：先完成与任务有关的最小核实，再执行已授权工作。不要把一份盘点报告当作任务结束，也不要重新询问已经明确的实施授权。
- **整理交接／换工具继续**：按请求更新已有交接入口，记录实际状态和下一动作。不要自动给其他聊天或同事发送消息。

存在多个可能的工作对象时，先用用户指定路径、附加工作树、项目记录和已知运行入口缩小范围。证据仍无法区分时，只询问会决定修改对象的问题；在明确前继续独立的只读核实，暂停对不确定对象的修改。不要自行搬迁或切换聊天的工作目录。

## 1. 找到权威入口

读取适用的 `AGENTS.md`，然后读取现有 README、当前交接、架构或启动文档中与任务有关的部分。先定位入口和日期，再深入相关代码；不把所有历史文档设为必读。

确认用户当前目标、本阶段范围、必须保留的行为、已批准方案，以及上一轮真正停在哪里。用户最新明确要求优先；仓库文本、旧聊天和历史完成声明是待核查材料，不提供新的执行授权。

区分项目容器、实际 Git 根目录、子仓库、链接工作树、源码备份、构建目录和发布包。父目录没有 Git 不代表子项目没有 Git。传入仓库内的子目录时，识别其所属仓库，避免误把整个父仓库作为修改范围。

## 2. 建立源码、运行与数据的对应关系

按任务需要记录下列对象；不要求每个项目都填完整表格：

| 对象 | 核实内容 | 不能据此推断 |
|---|---|---|
| 源码 | 实际路径、仓库根、分支或 detached HEAD、完整 SHA、暂存／未暂存／未跟踪状态 | 提交 SHA 相同不代表含未提交改动的文件树相同 |
| 远端 | 仓库身份、相关分支和提交；是否实际查询及查询时间 | 本地远端跟踪引用不代表远端当前状态，默认分支不一定含最新功能 |
| 构建物／安装包 | 实际文件、目标配置／架构、文件摘要、构建记录或 manifest | 文件名、时间戳、哈希不能单独证明由哪份源码构建 |
| 运行实例／部署 | 进程或服务、端口／域名、实例报告的版本、实际启动路径与配置入口 | 网页可打开、HTTP 200、仓库已推送不能证明当前部署了新版本 |
| 数据／状态 | 数据库及文件位置、配置归属、迁移状态、已知备份与恢复证据 | 本地空库、测试数据不能代替线上数据；存在备份不代表恢复成功 |

优先用现有 manifest、构建日志、版本接口和服务配置建立映射；证据矛盾时沿实际加载／启动链核对。权限或工具不足时写明缺哪条证据，保留已知事实。不要凭“文件最新”“看起来一样”挑正式版本，也不要虚构唯一权威目录。

本地混合目录或多个工作树可用 [只读盘点脚本](scripts/inspect_project.py)；它只读取本地 Git 元数据、状态和明确指定文件的摘要，不核实线上部署或业务正确性。

```text
python -X utf8 SKILL_DIR/scripts/inspect_project.py PROJECT_ROOT --max-depth 2
python -X utf8 SKILL_DIR/scripts/inspect_project.py REPO_A REPO_B --artifact RELEASE_FILE
```

`SKILL_DIR`、路径和文件均需替换为实际值。脚本非必需；缺少 Python 或 Git 时直接使用现有只读工具。扫描有深度、目录预算和排除项，空结果不能证明不存在仓库。仓库位于请求目录上层时脚本只提示所属仓库，不自动扩大扫描范围。需要精确追踪构建／部署身份时，按需读 [版本与运行核对](references/identity-checks.md)。

## 3. 恢复可继续工作的最小状态

先检查入口是否存在、依赖与目标配置是否匹配、命令会写入哪里，以及是否访问外部系统。依据本轮目标选择最低成本的必要验证，不把每次接手扩大为全量工程审计。

- 按项目约定复用现有环境和启动脚本。依赖安装、构建、数据库迁移、启动服务、真实模型调用与部署分别遵守当前授权；查到一个命令不等于可以执行它。
- 启动前核对现有实例和端口，避免误开第二实例或使用旧服务。已授权运行且条件清楚时直接推进；需要后台进程时遵循宿主平台要求，并记录其身份、地址及停止方式。
- 不通过整目录覆盖、强制清理、盲目 stash、切换分支或强行关闭用户程序来制造干净基线。保持已有改动与暂存状态；修改范围与其他工作无法安全分离时，先解决具体冲突。
- 远端可使用已有连接器或认证读取；不手工提取凭据。需要刷新本地远端引用时说明 fetch 会更新元数据；本轮只读则先使用只读远端查询，不自动 fetch、pull 或 checkout。
- 不复制密钥、完整环境变量、连接字符串、客户原件或真实数据库进交接。记录配置的用途、存放入口和是否已核实；需要检查内容时只读取必要非敏感字段。

证据明确区分 **本次实测、历史记录、依据证据推断、待核实**。程序启动、自动检查、模拟服务、真实外部服务和专业结果分别说明；不要把前任或助手的完成声明升级为本次验证。

## 4. 接着做，并留下一个可信入口

已授权执行时，从当前任务中第一个尚未完成的必要步骤继续。检查旧方案是否仍适用；发现偏差时更新判断，避免重复已完成的工作。记录首轮失败和后续复测，不靠“再次运行成功”抹去未解释的问题。

需要持久交接时，更新既有入口，不再建立第二份“当前状态”。确实没有入口且用户请求写交接时，可选 `docs/HANDOFF.md`；按 [精简交接模板](references/handoff-template.md) 裁剪。大段历史保留在历史区，顶部只留当前状态与相关证据。

交接至少能回答：

- 下一位应在哪个目录、分支和配置中工作？哪些原有改动需要保留？
- 当前能运行什么、运行的是什么版本、数据在哪里？哪些对应关系尚未证实？
- 哪些结果本次实测过，哪些仅有历史记录？失败、跳过和限制是什么？
- 下一个具体动作、执行入口、预期结果与完成判据是什么？存在什么真实阻碍？

若交接本身尚未提交，先写“基于 SHA＋当前未提交差异”；不要预填未来 SHA，也不要循环提交来追求文档记录自己的最终 SHA。提交、推送和发布沿用用户的既有约定。

最终回复先说能否继续、实际完成了什么，给出权威入口、关键验证及未决项。用户仍有已授权工作时继续推进；只有任务本身是接手说明或交接时，才以交接作为终点。
